# Appendix — Sources, Assumptions, and Open Questions

## Sources (facts, independently verifiable, not invented)

1. **Hyperliquid Arbitrum-bridge migration** — Hyperliquid's official account (X/Twitter, @HyperliquidX) and public documentation describe an active, in-progress migration from the legacy Arbitrum USDC bridge to native cross-chain minted USDC (CCTP-based). Hyperliquid's own developer docs state: *"The legacy bridge is deprecated."* This is current and directly affects the deposit rail this PoC (and the brief) assumes — flagged in §7 of the submission doc as something to re-verify against official sources at build time, per the brief's own instruction to reconfirm external service support before production.

2. **Hyperliquid deposit issues are a real, documented user problem** — independent third-party troubleshooting resources exist specifically for "Hyperliquid deposit stuck" scenarios (e.g. dedicated decision-tree guides for diagnosing stuck Arbitrum→Hyperliquid deposits), and their standard first instruction is explicitly "do not send a second deposit — first find your transaction hash." This is direct, independent evidence that the receipt-vs-credited ambiguity this PoC targets causes real duplicate-deposit behavior, not a hypothesis invented for this exercise.

3. **General crypto/DeFi onboarding friction (industry-wide, not Korea-specific)** — cited findings: ~90% of crypto users drop off within their first week; 38% abandon at the wallet-connection step alone; 70% of DeFi wallet connects never result in a first transaction; fiat/crypto on-ramp transactions fail up to 50% of the time in some reports. Sources: industry blog posts and reports from Formo, Sumsub, and general DeFi UX research aggregators (see conversation research). **These are general industry figures, not Exchange-O-specific or Korea-specific data**, and are cited only as evidence that this class of problem (multi-step crypto onboarding friction) is real and severe industry-wide — not as a claim about Exchange O's actual funnel.

4. **Korean exchange withdrawal whitelisting (Travel Rule)** — Korean exchanges (Upbit, Bithumb) require withdrawal-address whitelisting with ownership/identity verification, per FATF Travel Rule compliance, confirmed via exchange documentation and Travel Rule compliance guides. This is used in §2 to argue that "wrong network withdrawal from CEX" is a *lower*-probability risk for this specific user segment than for general Western on-ramp users — a structural mitigant, not a claim that the risk is zero.

5. **Korea Virtual Asset User Protection Act (2024)** and ongoing FSC (Financial Services Commission) regulatory activity — cited as the umbrella legal/regulatory context for any Korea-facing crypto product, per legal-industry summaries (e.g. Chambers Global Practice Guides, law-firm client alerts). Not a claim of specific compliance for Exchange O.

6. **Proposed Korean influencer holdings-disclosure rules** — reporting (Cointelegraph, via TradingView) describes South Korea moving toward requiring crypto/stock-promoting influencers to disclose their holdings. Cited as a live, current regulatory development relevant to the KOL-partner configuration surface, not as settled law at time of writing.

7. **Address poisoning as a real, current attack pattern** — documented by multiple wallet-security sources (Ledger Academy, Merkle Science) and real, large-dollar incident reports (e.g. a documented $12.25M loss case). Used to justify the full-address-confirmation UX layer (§3, Layer 4) as a real, not hypothetical, defense.

8. **Unlimited token approval as a known risk vector** — documented by MetaMask's own security guidance and referenced in real 2024 exploit post-mortems (Li.Fi, Socket/Bungee) where standing infinite approvals were the root exploited vector. Used to justify defaulting to exact-amount approval (§3, Layer 2).

## Assumptions (explicitly not backed by real Exchange O data — the brief withholds this data by design)

- **The receipt-vs-credited gap is the single biggest friction point.** This is a reasoned priority call (see §2's four-point justification), not a measured fact — the brief explicitly does not provide real funnel drop-off data. If real production data later shows a different step has higher absolute drop-off (e.g. the wallet-connection step itself, per the general industry figures in Source #3), this priority call should be revisited.
- **Korean CEX withdrawal whitelisting meaningfully reduces wrong-network-withdrawal risk for this user segment.** This is inferred from the *existence* of the whitelisting mechanism (Source #4), not from any measured incidence-rate data comparing Korean users to other markets.
- **The specific UX copy and thresholds used (e.g. the ~60-second window before flagging `AMBIGUOUS`) are PoC-scope placeholders**, not values derived from real bridging-latency data. Production values would need to be calibrated against real observed Hyperliquid bridging times.
- **The "primary metric" definition (percentage reaching `CREDITED` without re-deposit or support contact) assumes support-contact data would be available and attributable to a specific deposit** — this is a reasonable design goal, not something validated against any existing support/ticketing system, since none was provided.

## Open questions (would need real answers before production, not resolved by this PoC)

1. What is Hyperliquid's actual, current production deposit path at the time of a real launch — is the legacy Arbitrum bridge still live, or has it been fully replaced by native CCTP minting? (Source #1 shows this is actively in flux.)
2. What is the real distribution of time between "on-chain confirmed" and "Hyperliquid credited" in production? This PoC's mocked delay (15–30s) is illustrative only.
3. What is the actual duplicate-deposit incidence rate today, if any historical data exists internally at Project O? This PoC assumes it is a real, non-trivial problem based on external evidence (Source #2), but has no internal baseline to compare against.
4. What KOL-facing data/dashboard, if any, should partners be given visibility into regarding their referred users' deposit success/failure rates, and what are the privacy/consent boundaries on that data? Not designed or implemented in this PoC — flagged as an explicit gap, not an oversight.
5. Does Exchange O's actual production wallet infrastructure (Privy) expose the underlying wallet-role information (login vs. funding vs. trading account) in a way that maps cleanly onto the wallet-role labeling implemented here, or would that require additional integration work?
6. What are the actual legal/compliance requirements for the KOL conflict-of-interest disclosure banner's specific wording, in the jurisdictions Exchange O actually operates in? This PoC's banner text is a reasonable illustrative approach, not reviewed by counsel.
